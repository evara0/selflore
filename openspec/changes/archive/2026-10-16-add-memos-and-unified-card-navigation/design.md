## Context

动机见 proposal.md。现有实现使用 FastAPI、Pydantic、PostgreSQL 和 React Router／TanStack Query；本变更跨导航、卡片、关系、合集、统计和迁移，需在实施前明确共同契约。

- `App.tsx` 当前定义知识、观点、合集、我的四个主导航，移动端在其中插入中央新建动作；原有底栏布局可复用。
- `Knowledge.tsx` 的全部查询明确限制 `knowledge,reference`，观点使用独立列表和主题。合并入口需要真正合并查询、渲染和筛选，不能仅更改导航文案。
- `workspace.py` 和 `lib/workspace.tsx` 将类型限定为三类；卡片服务已有创建幂等、父卡片修订、生命周期、搜索文本及关联事务。详情和选择器中多处将非资料／非观点直接当作知识，必须改为明确类型分支。
- `0005_reference_media.sql` 是当前最新迁移。附件仅允许资料；知识复习由数据库同类型约束保护；来源扩展曾处理旧创建摘要兼容，新增默认字段也需沿用该保护。
- 现有 `card_links` 只区分正文及手动来源，不能直接表达某一清单条目来源；合集引用卡片不复制内容。
- 个人学习日历按 `card_created/card_updated/reviewed` 活动聚合，直接复用这些活动记录备忘会误增连续天数。
- `apps/api/app/db_backup.py` 的全表快照可涵盖新增表，但应用读取核验存在固定业务表清单，必须扩展；源码保留 `apps/api/app/card-schema-capability`，当前v2发布包以manifest的features、迁移清单和API哈希执行更严格的兼容校验。
- 当前工作区另有 `App.css` 修改和 `inline-mobile-builder-credit` 规划；本次只写新变更目录。实施时应保留这些已有成果。

## Goals / Non-Goals

**Goals:**

- 使用四个主页面承载内容浏览、备忘处理、合集组织和个人信息，保留现有中央新建动作及旧链接。
- 在共同卡片身份上增加结构化条目，使编辑、完成、汇总和引用使用同一份数据及修订边界。
- 让备忘快速保存，不要求用户先决定分类、出处或形成观点；确保统计、权限和恢复可靠。

**Non-Goals:**

- 不引入任务项目、子任务、时间规划、截止日期、提醒、通知、重复任务、多人协作或自动学习计划。
- 不在本变更接入此前讨论的免费来源解析、OCR、AI 分类或任何付费服务。
- 不支持备忘图片；图片仍收录为资料，通过关联连接备忘。第一版不提供备忘类型或普通文字／清单的保存后转换。
- 不重构发布执行器或备份体系，只扩展新结构必须使用的核验和能力门禁。本次规划不启动应用、执行迁移或发布。

## Decisions

### 1. 导航按使用场景分组，页面内筛选内容类型

主导航固定为 `卡片 / 备忘 / 合集 / 我的`，桌面和移动共用定义。保留移动中央新建按钮；它是动作，不是第五个目的页面。卡片页使用 `全部 / 资料 / 事实知识 / 观点` 筛选，全部显式请求三类内容，备忘仅在备忘区浏览。

将知识及观点列表的共同查询、搜索和分页提取到统一列表，按明确类型选择资料缩略图、知识答案揭示、观点摘要。观点保留主题、关联排序和详情阅读，知识与资料分类保持原类型约束；切换类型清除不兼容主题和页码。复习动作保留为事实知识入口，复习条带仅出现在事实知识筛选，避免资料和观点被复习控件挤占。

替代方案：新增第五导航已被用户排除；把备忘藏到我的会增加日常处理路径；仅把知识重命名而保留单独观点入口无法腾出位置。

### 2. 规范新路由并以适配器保留旧路由

| 目的 | 新路由与行为 |
| --- | --- |
| 三类卡片列表 | `/cards?type=all\|reference\|knowledge\|opinion`，其他条件继续使用查询参数 |
| 三类卡片详情 | `/cards/:id`，类型由真实数据决定，均高亮卡片 |
| 备忘列表 | `/memos?view=all\|note\|checklist\|open` |
| 备忘详情及条目定位 | `/memos/:id?item=<uuid>`，高亮备忘 |
| 编辑及新建 | 保留 `/cards/:id/edit`、`/new`，新增 `kind=memo&memo_format=note\|checklist` |
| 复习 | 保留 `/knowledge/review`，高亮卡片，仍只调度知识 |

`/knowledge` 适配到卡片列表，保留原显式类型、搜索、标签、收藏、分类、归档、排序和页码；原无类型的全部入口现在进入新的三类全部视图。旧 `/knowledge/cards/:id`、`/knowledge/references/:id` 适配新详情。`/opinions` 适配 `type=opinion`，保留 `q/topic/state/sort/offset`；`card=<id>` 保留所选观点并可打开详情。旧列表链接仍能恢复其有效条件，类型不兼容的条件按现有规则清理。

URL 显式筛选优先，其次是浏览器历史，最后才是从主导航进入时的类型偏好；偏好只保存按账号隔离的类型枚举，不保存搜索词、内容或卡片ID。游客使用单独键，存储异常退化为全部。账户切换清理内存缓存和当前选择；导航、品牌、认证成功、退出、404返回、详情返回和关联链接统一采用规范路由。进入详情后返回保留来处列表查询，而非统一返回无筛选列表。

### 3. 备忘复用卡片身份，形式单独表达

在 `app.cards` 新增 `kind='memo'` 和仅备忘使用的 `memo_format='note'|'checklist'`。不扩大现有 `form` 的含义，`form` 继续仅为知识问答／填空；非备忘 `memo_format` 为NULL，备忘的 `form/question_md/answer_md/note_md` 为NULL，`body_md` 是可选说明正文。普通备忘允许只有非空标题；清单还必须有1至200个有效条目。标题沿用200字符，正文沿用64 KiB限制。

备忘共享来源、标签和收藏字段，但编辑器默认精简，仅显示标题、正文或条目，标签／来源放入可选详情；第一版 `topic_ids` 必须为空，不新增一套备忘分类。附件继续仅属于资料。类型及两种备忘形式创建后固定，避免无意切换丢失完成和关联记录。

替代方案：把备忘伪装为资料会违背原材料要求；把清单塞进 Markdown 勾选语法无法可靠支持条目身份、汇总与并发；把任务建成完全独立于卡片的对象会重复引用、归档、合集和权限逻辑。

### 4. 条目和关联使用独立关系表

建议增量结构如下，最终DDL沿用现有迁移风格：

| 对象 | 关键属性与约束 |
| --- | --- |
| `cards.memo_format` | 可空枚举；备忘必填，其他类型必须为空；与卡片类型、内容形状共同约束 |
| `memo_items` | UUID主键、`owner_id`、`memo_card_id`、`text`、`position`、`is_completed`、`completed_at`、创建及修改时间 |
| `memo_item_links` | `owner_id`、`memo_card_id`、`item_id`、`target_card_id`；同项同目标唯一 |

条目文字去首尾空白后1至2000字符，位置为0至199，父卡片内位置唯一且可延迟校验。条目以同用户复合外键绑定备忘父卡片；提交时约束父卡片必须为清单、条目数为1至200、普通备忘不得有条目。已存在条目的ID、所有者和父卡片不可被修改；新增项使用客户端预生成UUID，创建重试保留相同ID。

`is_completed` 在SQL、Python和JSON中采用同一肯定式名称，非空、默认false，含义为“该条目已完成”。`completed_at` 由服务器维护，并约束已完成时非空、未完成时为空；文本编辑和排序不重置它，撤销后再次完成使用新的时间。整卡进度由条目派生，不额外存 `is_completed` 到父卡片。生命周期继续用枚举，避免与完成布尔值混用。

条目关联通过同用户复合外键同时约束父项及目标，最多20个目标，禁止重复、指向所属清单本身和跨用户。每项关联的原始记录只存于 `memo_item_links`，不向 `card_links` 写镜像；关联列表和反向链接通过查询合并正文、手动和条目三类来源，在卡片级去重，并返回具体条目定位信息。

条目关联删去只影响该来源；已有正文和手动关联照常保留。条目文字按纯文本安全渲染，正文继续使用已有安全 Markdown。不可用目标仅返回必要的状态及标题，不暴露完整正文；恢复后原稳定关联重新可读。

### 5. 采用父卡片修订保护全部清单操作

| 接口 | 契约 |
| --- | --- |
| `POST /api/cards` | 增加备忘类型、形式和条目数组，沿用 `client_request_id`；条目输入包括ID、文字、完成目标状态及目标ID集合 |
| `GET/PATCH /api/cards/:id` | 详情包含有序条目、完成时间和关联；PATCH显式携带条目数组才替换集合，省略时保留，要求 `expected_revision` |
| `PUT /api/cards/:id/memo-items/order` | 完整条目ID序列及父修订，仅重排不增删；拒绝遗漏、重复、外来ID |
| `PATCH /api/cards/:id/memo-items/:item_id` | 仅提交 `is_completed` 与父修订，供详情和汇总快速勾选，返回最新父修订、条目及进度 |
| `GET /api/memo-items?is_completed=false` | 服务端直接分页正常清单的未完成项，支持搜索，返回父ID、标题、修订、条目及关联 |

新增 `memo_items` 在旧类型请求中默认为空，`memo_format` 默认为NULL。非备忘携带条目或备忘形式应拒绝。卡片PATCH严格区分未提供与空数组，避免只修改收藏／来源时清空条目；输入不接受客户端设置服务器完成时间。完整条目编辑根据保留ID计算增删改，不全删重建，且不得把其他父卡片已有条目ID挪过来。

所有内容写入先锁父卡片，校验所有者、正常生命周期和修订，再验证条目及目标；全部在同一事务保存条目、顺序、关联、搜索文本、父修订和活动。归档／回收站备忘仅允许合法的生命周期操作，不允许修改内容或完成条目。直接SQL也必须有结构及同用户保护，不能只靠API。

快速完成接口提交目标布尔值而非toggle。相同修订且状态无变化时返回当前结果，不增修订、改完成时间或写活动；旧修订一律409并要求重新读取。网络响应丢失后的重试可能遇到409，客户端重查后以真实状态为准，不再翻转。编辑器冲突保留全部输入，快速勾选默认等待成功再提交视觉状态，失败保留原状态及明确重试提示。

旧创建摘要必须保留已有兼容路径：旧三类请求且新增字段均为默认时，接受迁移前摘要；备忘非默认形式或条目不得被剔除。清单初始已完成项的时间同样由服务器生成。旧 `form` 和卡片类型依旧不可通过PATCH修改。

### 6. 汇总按条目查询，卡片按父记录搜索

卡片页始终显式查询 `kinds=knowledge,reference,opinion`；备忘页显式查询 `kind=memo`，形式使用单独筛选。通用 `/api/cards` 无类型限制时可以返回四类，因此所有现有选择器、回收站和类型标签必须显式支持四类；`kind=knowledge` 等旧单类请求保持原语义。列表请求扩展 `memo_format` 筛选，只有选择备忘时可使用。`/cards/summary` 增加独立备忘数量，卡片区的收藏、待整理等聚合按三类内容限定，备忘区的卡片及事项总数分别查询，避免类型混算。

服务端未完成事项查询从 `memo_items` JOIN正常状态清单，执行count和分页，建议排序为父卡片更新时间降序、父ID、条目位置及条目ID。文字匹配所属清单标题或当前项，列表搜索则可匹配整张备忘的正文与任意项；父卡片搜索使用更新后的 `search_text`，不因多项命中重复返回同一备忘。新增父卡片／完成状态／顺序索引支持读取；仅按实际查询计划增加索引，不新增搜索服务。

汇总展示项文字、所属清单和关联；进入父清单携带条目ID，已删除条目提示定位不可用并仍能看父清单。勾选后重新取得真实总数及有效页码，当前末页变空时回到有效前页。完成数、总项数按父卡片聚合；备忘卡数量和未完成项数量分别显示。

### 7. 关联、合集和活动共同适配第四类型

所有 `cardKindName/cardUrl`、卡片选择器、Markdown引用、详情、回收站和关联列表采用明确的四类型处理。允许备忘正文引用本人四类卡片，条目关联支持其他备忘；目标生命周期规则沿用现有安全规则。

合集增加 `memo_count`，引用备忘而不复制条目。合集内展示文字或只读清单及进度，进入原备忘才可完成／编辑，保持“翻阅不写入”的语义。成员排序、归档不可用和恢复沿用原行为。

个人主页增加独立 `memos` 数量；事件增加 `memo_created/memo_updated/memo_organized/memo_item_completed/memo_item_reopened`，相应更新数据库事件约束和活动筛选。一次显式完成操作只记一次对应活动；完整清单编辑含多项变化时记一条 `memo_updated`，不额外生成多项完成活动。学习日历仍仅统计原三类内容事件和评价，备忘事件不进入连续天数和掌握统计。可记录用户做过的事项，但不宣称掌握知识。

### 8. 游客复用同一导航，写入仍需认证

扩展 `readDemo` 支持统一列表筛选、普通备忘、部分完成清单及未完成项汇总，并使用已有演示空间缓存。示例条目、关联和进度来自同一份静态数据；不使用任何用户原图或真实内容。勾选等写入触发登录，不改变示例状态、不发送业务请求。登录、退出和会话过期清理缓存及当前条目交互，不复用其他用户偏好。

## Risks / Trade-offs

- [统一页面使观点多一次类型选择] → 保留按账号的最近类型及URL历史；移动端不增加主导航。
- [旧路由仍有大量入站引用] → 兼容适配所有现有详情、筛选及 `card` 查询，覆盖刷新、返回、分享及认证跳转。
- [单一父修订增加不同条目间冲突] → 与现有卡片一致，第一版优先防止覆盖；保留编辑输入并可重新读取，暂不引入合并或独立条目版本。
- [清单全量修改可能误清空或挪用条目] → 区分省略／空值、保留稳定ID，数据库与服务均校验归属，限制200项并做事务校验。
- [多种关联来源去重时丢失条目定位] → 保留来源和条目ID，只在卡片总览去重，不把删除源关系变为删除全部关系。
- [普通备忘扩展为任务系统造成复杂度] → 仅支持两种形式、单层清单和未完成汇总；后续需求另立变更。
- [新字段破坏旧幂等或旧包读取备忘] → 增加旧摘要测试及备忘结构能力门禁，不自动回退到只识别三类卡片的包。
- [变更涉及面较广] → 按数据库、服务、导航、备忘界面、集成及验证分组推进，保持既有资料上传和知识复习回归。

## Migration Plan

1. 实施时重新核对最新迁移编号，在 `0005` 之后追加下一版本，不修改已执行SQL。备份旧库；演练使用隔离实例，不能把测试指向日常库。
2. 在同一迁移事务内扩展卡片形状和类型、备忘形式、条目与关联表、事件类型、索引、完整性约束及应用角色授权。旧三类卡片新增字段为空，不回填备忘，不转换数据，不改变复习和媒体。
3. 覆盖空库和带账号、图片、引用、合集及复习历史的旧库升级；验证重跑、失败回滚、直接SQL越权、应用角色权限和旧创建重试。
4. 更新源码能力标记为 `reference-memo-v1`，并在当前v2 manifest中加入与0006迁移对应的 `features.memo`；旧清单缺省为不支持备忘。继续要求回退包具有相同features、完整迁移清单及API哈希，保留比单纯相同标记更严格的现有门禁。核对备份策略及恢复读取清单包含新增表。
5. 同一发布包交付服务端和前端，先人工备份，再暂存迁移并激活。应用启动不自动迁移；失败不运行数据库降级。迁移失败保持旧服务，迁移成功后若新服务失败，只能按相同新能力版本回退应用，否则保留指针报告人工处理。
6. 在隔离环境备份并恢复含普通备忘、部分完成条目、关联和既有图片的样本，验证全表摘要、权限、应用详情、汇总和知识复习不变。最后完成移动及桌面浏览验收并更新维护卡、迁移及发布说明；归档仍需用户另行要求。
